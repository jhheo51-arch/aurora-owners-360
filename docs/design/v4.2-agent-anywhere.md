# v4.2 설계 초안 — 어느 화면에서든 쓰는 VOC Care Assistant

> 상태: **✅ 구현 완료 (2026-10-15, 태그 `v4.2`, Agent v12, 결과는 PRD §22)**. 아래는 설계 당시 기록. 원래 상태: 설계 초안 (2026-10-15, 사이드 챗). 구현 전. 원래 세션의 AICX(v4.1) 작업과 겹치지 않도록 이 파일만 새로 만들었고, PRD·Agent·코드는 바꾸지 않았다. AICX가 끝난 뒤 이 문서를 PRD 새 절로 옮기고 구현한다.

## 1. 왜 바꾸나
- 지금 VOC Care Assistant의 액션 6개는 모두 **열려 있는 레코드 ID**(`currentRecordId`)를 입력으로 받는다(PRD Q54·Q56).
- 그래서 VOC·고객 차량 화면이 아니면 "VOC를 연 뒤 새 대화를 시작해 주세요"라고만 답한다. 홈·목록·다른 앱에서는 아무 일도 못 한다.
- 처음에는 잘못된 대상을 고르는 실수를 막으려고 범위를 좁혔다. v4.2에서는 **대화로 대상을 찾되, 모호하면 되묻는** 방식으로 넓힌다.

## 2. 목표 (사용 예)
| 화면 | 사용자 말 | 기대 동작 |
|---|---|---|
| 홈 | "00001028 정리해 줘" | VOC 번호로 찾아 5줄 요약 |
| 홈 | "한서아 고객 VOC 요약해 줘" | 차주의 진행 중 VOC 2건 → 어느 건인지 물음 → 고른 건 요약 |
| 목록 | "VEH-0007 레몬법 해당돼?" | 차량 번호로 찾아 레몬법 판정 |
| 다른 앱 | "34바 5678 차 반복 결함 있어?" | 번호판으로 차량을 찾아 반복 결함 확인 |
| 아무 화면 | "기한 임박 VOC 뭐 있어?" | 업무 조회 목록(기한 순 최대 5건) |
| 아무 화면 | "리콜 경보 있어?" | 진행 중 리콜 경보 목록 |
| VOC 화면 | "이거 정리해 줘" | 지금처럼 열린 레코드 사용(대화로 찾기보다 우선) |

## 3. 대상 찾기 규칙
**우선순위**: ① 대화에 대상이 명시되면 그것 → ② 열린 레코드가 오로라 VOC·고객 차량·차주면 그것 → ③ 둘 다 없으면 "어떤 VOC인가요? VOC 번호, 차량 번호, 번호판, 차주 이름 중 하나를 알려 주세요."

| 입력 형태 | 인식 패턴 | 찾는 곳 |
|---|---|---|
| VOC 번호 | 숫자 8자리(`00001028`), "VOC 1028"처럼 뒷자리만도 허용 | `Case.CaseNumber` (VOC_Status__c 있는 오로라 VOC만) |
| 차량 번호 | `VEH-0007`, `VEH 7` | `Vehicle__c.Name` |
| 번호판 | `34바 5678`(공백 무시) | `Vehicle__c.Plate_Number__c` |
| VIN | 17자리 영숫자 | `Vehicle__c.VIN__c` |
| 차주 이름 | 한글 2~4자 | `Contact.Name` 중 **오로라 차주만**(결정 D1) |
| 보상 번호 | `CMP-0002` | `Compensation__c.Name` → 연결 VOC |

**결과 처리**
- 1건: 바로 사용하고 "VOC 00001028 · 주행 중 브레이크 경고등 점등 기준으로 답합니다"처럼 대상을 먼저 밝힌다.
- 여러 건: 최대 5건을 번호 목록으로 보여 주고 고르게 한다(결정 D2). 차주 → VOC는 진행 중을 먼저, 종결은 "종결 포함"이라고 할 때만(결정 D3).
- 0건: "찾지 못했습니다"와 함께 입력 예시를 안내한다. 추측해서 비슷한 레코드를 고르지 않는다.
- 실습 데이터(새싹·Ohana Case, 실습 연락처)는 검색하지 않는다.

## 4. 바뀌는 구성
| 구분 | 이름 | 변경 |
|---|---|---|
| 새 Apex 액션 | `AuroraRecordFinder` | 입력 `query`(사용자 말), `contextRecordId`(열린 레코드, 없을 수 있음), `targetType`(VOC/VEHICLE/ANY). 출력 `status`(FOUND/MULTIPLE/NOT_FOUND), `recordId`, `label`, `candidates`(번호 목록 문구) |
| 새 Apex 액션 | `AuroraWorkQueryAction` | 입력 `queryType`(OPEN/DUE_SOON/OVERDUE/SAFETY/ESCALATED/RECALL), `staffName`(선택). 출력 목록 문구. 읽기 전용. 홈 히어로(`AuroraCardController.getHomeHero`)와 같은 기준 재사용 |
| 기존 Apex 액션 3개 | 유사 사례·레몬법·이관 | 입력 `recordId`를 `currentRecordId` 고정 바인딩 대신 **찾은 ID**를 받도록. 액션 코드는 그대로(이미 ID 문자열을 받음) |
| Prompt 액션 3개 | VOC 요약·답변 초안·인계 요약 | `Input:Case`에 찾은 VOC ID를 넣도록 지시문 변경. 템플릿 자체는 변경 없음 |
| 새 토픽 | `work_query` "업무 조회" | "내 VOC", "기한 임박", "안전 결함 진행 중", "이관 대기", "리콜 경보" 질문 |
| 기존 토픽 5개 | 지시문 | "currentObjectApiName이 Case가 아니면 안내" → "먼저 대상 찾기 액션 실행, MULTIPLE이면 되묻기, NOT_FOUND면 입력 예시 안내" |
| Agent 변수 | `targetRecordId`(mutable string, Internal) | 찾은 대상을 대화 동안 기억해 "그거 답변 초안도 써 줘" 같은 후속 질문에 재사용(Agent Script의 변수 대입 문법은 구현 때 `sf agent validate`로 확인 — 안 되면 매 턴 찾기) |
| 인사말 | welcome | "VOC 번호·차량 번호·차주 이름으로 어느 화면에서든 물어보세요" 예시로 교체 |

## 5. 가드레일 (v4와 동일 + 추가)
- 기록을 바꾸는 이관 요청은 **대상이 1건으로 확정되고**, 사용자가 확인한 뒤에만 실행. 후보가 여러 건이면 실행하지 않음.
- 대상이 바뀌면(다른 번호를 말하면) 이전 대상의 맥락을 쓰지 않고 새로 찾는다.
- 업무 조회는 목록과 건수만, 개인 연락처(전화·이메일)는 표시하지 않는다.
- 종결·보상 승인·유형 변경은 여전히 사람만. 사람·AI 같은 규칙 유지.
- 직원용 Agent라 접근은 지금처럼 권한 세트 `Aurora_Owners_360_User` 사용자만.
